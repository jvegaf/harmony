# Design: Upgrade Electron 33→43 + better-sqlite3 12→13 (N-API)

Change: `upgrade-electron-better-sqlite3` · 2026-08-23 · Answers `proposal.md`; constrained by `specs/runtime-toolchain/spec.md` (8 requirements / 11 scenarios).

## Technical Approach

Joint bump exploiting better-sqlite3 v13's N-API migration (release-verified: prebuilds shipped inside the tarball, `prebuild-install` removed, additive JS API) to dissolve the Electron-ABI coupling. One binary serves system Node AND the Electron main process. Four workstreams: version bumps; `nodeSqliteStub` removal; toolchain reconciliation for Electron ≥42's lazy-download model; DB-test un-skip with feature detection. Three-process model, IPC surface, schema, and migrations untouched.

## Architecture Decisions

### D1: Delete `nodeSqliteStub()` outright — do not gate

**Choice**: Remove function (electron.vite.config.ts L5–23) and registration (L62).
**Alternatives**: gate on Electron major; invert stub logic.
**Rationale**: Repo ships E43 only; `node:sqlite` is builtin since E35 (Node ≥22.13). Keeping the stub replaces a *working* builtin require with a thrower and breaks undici/cheerio feature detection (HIGH risk). Gating preserves dead code for majors we never ship.

### D2: `postinstall` → `install-electron`

**Choice**: `"postinstall": "install-electron"` (bin shipped by the electron package; E42 release notes verify it).
**Alternatives**: drop postinstall (lazy first-run fetch); keep `electron-builder install-app-deps`.
**Rationale**: electron-vite 5.x spawns the binary without triggering the lazy download (issue #904 open) → fresh `pnpm dev` fails "Electron failed to install correctly". Eager fetch restores deterministic dev/CI. `install-app-deps` is worse than useless now: rebuilding an N-API module against Electron headers would overwrite the cross-runtime prebuild with an ABI-specific binary — exactly what this change eliminates.

### D3: `allowBuilds` reconciliation

**Choice**: Keep `better-sqlite3` (its install script validates/places the bundled prebuild and compiles when a platform lacks one — source fallback must stay runnable), `esbuild`, `electron-winstaller`. Remove `electron` (E≥42 package ships no install script; dead config).
**Alternatives**: keep all entries.
**Rationale**: minimal honest whitelist documents the new no-rebuild model.

### D4: `asarUnpack` keeps whole-package glob

**Choice**: Retain `node_modules/better-sqlite3` and `out/main/chunks/*.node`; retain `npmRebuild: false`; `.npmrc` unchanged.
**Alternatives**: narrow globs targeting v13's internal `prebuilds/<platform>-<arch>/` layout; drop unpack (N-API might load from asar).
**Rationale**: `.node` files can never load from inside asar — unpacking stays **required**, not optional. Whole-directory unpack is layout-agnostic across 13.x patches; narrow globs break on upstream reshuffles.

### D5: Un-skip DB tests behind feature detection

**Choice**: Top-level probe — attempt to open `:memory:` via better-sqlite3 in try/catch; `describe.skipIf(!probe.ok)(...)`; log the failure reason loudly when skipping. Rewrite the stale ABI header comment.
**Alternatives**: unconditional un-skip; sql.js substitution.
**Rationale**: satisfies the spec's fallback scenario (explicit logged skip on platforms lacking prebuilds) while making linux-x64 CI run the real suite against real migrations from `drizzle/`.

### D6: Typing-drift containment (@types/better-sqlite3 ^9)

**Choice**: Fixes limited to explicit type narrowings at call boundaries inside `src/main/lib/db/**` + the test file.
**Alternatives**: broad refactor to new typing idioms.
**Rationale**: proposal marks refactors out of scope; typecheck is the gate.

## Data Flow

```
pnpm install
 ├─ allowBuilds → better-sqlite3 install script (validate/place N-API prebuild | compile fallback)
 └─ postinstall → install-electron (binary → node_modules/electron/dist)
                       │
        ONE cross-runtime .node binary
                       ▼
   Vitest/system Node (tests, scripts/*.js) ◄──► Electron main (pnpm dev / packaged app)
                                                └─ Database singleton → drizzle → harmony.db (unchanged)
```

Runtime DB path is untouched: main-process-only, workers excluded (grep-verified: importers are `database.ts`, the test, and two dev scripts).

## Testing Strategy

| Spec requirement | Proof |
|---|---|
| Clean install resolves ranges | Fresh clone `pnpm install` + `pnpm ls electron better-sqlite3 @types/better-sqlite3 drizzle-orm` |
| Driver loads (Node / Electron) | `node -e "require('better-sqlite3')"` exit 0; `pnpm dev` logs `[db] Database initialized` |
| Stub removal preserves scraping | Built bundle contains no stub; bandcamp/soundcloud/googlethis IPC flows exercised live, no `ERR_UNKNOWN_BUILTIN_MODULE` |
| DB tests un-skipped | `pnpm run test:run` reports executed passing DB tests (unique-path, upsert dedup, migration index) — natural RED→GREEN: pre-bump they fail to load the native module |
| Feature-detected fallback | Probe logs skip reason; simulated by hiding the prebuild locally once |
| Typecheck gate | `pnpm run typecheck` zero errors on @types ^9 |
| Hands-off bootstrap | Clean checkout: install → typecheck → test:run → build, zero manual steps, no missing-binary failure |
| Packaged smoke | `pnpm run build:linux` AppImage boots; migrations idempotent; scan + playlist CRUD |
| Boundary diff | `git diff -- src/preload src/main/lib/db/schema.ts drizzle/` empty |

## Threat Matrix

N/A — no routing, shell-command, subprocess, VCS/PR-automation, executable-file-classification, or process-integration boundary in application code. The single npm-script edit (D2) is declarative tooling config proven by the hands-off bootstrap scenario, not a code-level process integration.

## Migration / Rollout

No data migration: SQLite file format stable across library versions; migration set unchanged; `migrate()` idempotent. Recommend copying `~/.config/harmony/database/` before first prod run. Code rollback: `git revert` PR + `pnpm install` (legacy postinstall auto-rebuilds v12 for E33 ABI).
